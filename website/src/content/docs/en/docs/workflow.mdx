LittleDevTeam organizes substantial engineering work into small, verifiable steps. It chooses the smallest useful plan and tool effort for the actual task.

## The lifecycle

| State phase | Purpose | Concrete output |
| --- | --- | --- |
| `INTAKE` | Receive the request | Goal and boundaries |
| `DISCOVERY` | Inspect rules, sources, and working state | Actual state and open questions |
| `SPECIFICATION` | Clarify desired behavior | Observable requirements |
| `ARCHITECTURE` | Design the solution and milestone | Versioned proposal with required checks |
| `APPROVAL` with `architecture` | Human architecture decision | Approval or revision request for the concrete scope |
| `IMPLEMENTATION` | Implement one approved milestone | Bounded source change |
| `VERIFICATION` | Execute relevant checks | Actual outcomes and limitations |
| `PR_REVIEW` | Review and hand off the result | Concrete revision, review, and source snapshot |
| `APPROVAL` with `iteration` | Evaluate the result | Human decision about this revision |
| `NEXT_ITERATION` | Select the next step | A new concrete milestone |

`APPROVAL` is one phase with two different `approval_stage` values. “PR REVIEW” is persisted as `PR_REVIEW` in JSON. Failed checks or rejected results lead to repair and renewed verification within the current scope. A material design change returns to the architecture decision.

## Choose the appropriate profile

| Profile | Typical use | Consequence |
| --- | --- | --- |
| **Lean** | A small, bounded change | Short proposal and targeted checks |
| **Balanced** | Ordinary work across components | Proportionate architecture, small milestones, and relevant checks; the default |
| **Rigorous** | Significant security, migration, or reliability risk | More evidence and actual independent-review requirements |

Profiles adjust effort, not your authority. No profile replaces actual approval or turns a failed mandatory check into success. Changing the profile changes the scope fingerprint and may require renewed architecture approval.

## Roles and tools

Roles describe responsibilities, such as architecture, implementation, verification, and integration. A lead agent chooses the appropriate division of work, assigns bounded tasks, and integrates the results. Additional agents are useful when tasks can be separated cleanly and the session makes those agents available and permits their use. A fixed team size is not guaranteed.

One agent can perform several roles in sequence. Its own review remains self-review. Independent review requires another actual agent or person to inspect the concrete change and its evidence.

External skills supply reusable instructions, references, or tools. They do not create agents. Registry entries describe candidates; selection, consent, and any installation are separate steps. The skill does not supply a background service.
